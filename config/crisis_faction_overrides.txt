# Crisis-faction override config (D-7/P-5) — hand-maintained, checked in, loaded by
# pipeline/crisis_faction_overrides.py, consumed by pipeline/crisis_faction.py.
#
# Zero technology data is hand-authored (CLAUDE.md / spec/P-10-performance-automation.md); this
# file is configuration, not technology data, in the same category as empire profiles, gate
# patterns, overwrite overrides, and the P-13 lock-reason override table — all hand-maintained
# because they either encode an editorial decision or paper over a corpus shape the automatic
# rule can't resolve unambiguously.
#
# pipeline/crisis_faction.py derives membership automatically in D-7's order: technology ID
# (pipeline/crisis_faction.py's classify_by_tech_id), then prerequisite-chain inheritance
# (classify_by_prerequisite_inheritance — a technology with no ID hint of its own inherits a
# faction only when EVERY one of its rendered prerequisites already belongs to the same single
# faction). This file is the fallback for anything neither step resolves, and can also CORRECT a
# step 1/2 result that turns out wrong (an override always wins when present, per D-7 — this is
# the one hand-maintained file in the project that is explicitly allowed to override an
# automatic result, not just fill a gap, because faction membership is closer to an editorial
# call than any of this project's other overwrite/lock-reason tables).
#
# pipeline/crisis_faction.py's own module docstring records one case that was tried
# automatically (via a `potential`-block crisis-flag reference, not prerequisite inheritance) and
# found to be a FALSE POSITIVE rather than a real membership signal -- it is deliberately NOT an
# entry here, because the correct classification (standard lane) is already what the automatic
# derivation produces for it without an override:
#   - giga_tech_tetradimensional_engineering (a standard physics tech with an alternate
#     Blokkat-crisis-progress unlock path, not a Blokkats-lane technology)
#
# Format: one entry per line, technology key/faction separated by ' = ', followed by a required
# '#' justification (never optional — a line without one is a config error, not a silent skip):
#
#   <technology key> = <faction: Aeternum | Blokkats | Compound | Sirenalia | Katzenartig Imperium | None>  # <justification>
#
# `None` forces a technology into the standard-progression lane, overriding an automatic step 1/2
# match that turns out wrong.
#
# --- Real entries below ---
#
# Both entries below correct the SAME step-1/2 result: `tech_sm_autocannons` was previously
# documented as a second confirmed false positive alongside giga_tech_tetradimensional_engineering
# above (EHOF/Urmazin-trader content referencing a Compound weapon-compatibility bypass flag, "not
# a membership signal"). That reasoning addressed identity (is this technology itself
# Compound-authored content?) and correctly found no ID/category evidence that it is. It did not
# address reachability: does `giga_special_tech_compound_weapon_bypass` open a real path to
# researching the technology that a Compound-crisis empire, and only a Compound-crisis empire, can
# take? Checked directly against the raw corpus, it does: the flag's sole setter anywhere in the
# vendored corpus is `vendor/mods/gigastructures/events/giga_compound_situation_09.txt:113`,
# inside the Compound situation's own event chain (`common/situations/giga_compound_09.txt`
# drives it) — no other event, effect, or on_action sets it. A technology whose only
# non-`has_technology` unlock branch is gated behind a flag with that provenance is Compound
# content wearing an EHOF technology's clothes, not EHOF content that happens to reference a
# Compound flag in passing.
#
# `tech_qnm_disruptors` (giga_08_ehof_components.txt) was not previously documented at all --
# found this session by re-reading the same file `tech_sm_autocannons` lives in. It carries the
# byte-for-byte identical `potential` shape: `OR = { AND = { has_technology = <tier-3 baseline>,
# has_technology = tech_qnm_utilities }, has_country_flag =
# giga_special_tech_compound_weapon_bypass }`. Same flag, same sole setter, same reasoning
# applies without modification.
#
# Why this is an override and not a rule change to pipeline/crisis_faction.py: the evidence for
# both entries lives in `vendor/mods/gigastructures/events/`, a directory this project has never
# declared as a required extraction source (CLAUDE.md's "Required directories, per source" lists
# `common/technology`, `common/scripted_variables`, `common/scripted_triggers`,
# `common/ascension_perks`, `common/inline_scripts`, `localisation/english`, and two icon
# directories -- `events/` is not among them). Teaching the classifier to resolve
# `has_country_flag` provenance generally would mean adding `events/` as a required source and
# making event-namespace string inference (which files set which flags) load-bearing for layout
# output -- a materially larger scope change than the two nodes it would resolve. A one-off,
# reviewed override is the proportionate response for two nodes; folding this into the general
# classifier is not, absent more corpus evidence that the pattern recurs.
#
# A rule was also considered and rejected as incoherent: "classify a technology's `OR` branch as
# Compound-gated when a `has_technology` reference inside that branch resolves to Compound
# content." Run literally against these two technologies' `has_country_flag` branch, that rule
# reports zero matches -- correctly, because that branch contains no `has_technology` reference
# at all for a has_technology-scoped test to evaluate. Zero was the right output for the rule as
# specified; it was the rule's scope, not the corpus, that was wrong, which is why these two
# nodes are handled here by direct flag-provenance evidence instead.
#
# This override does NOT track corpus growth. If a future Gigastructures update adds more
# technologies gated behind a Compound-situation bypass flag by the same pattern, they will
# silently classify Standard until someone notices and adds an entry here -- there is no
# generalised detector watching for this shape. `tests/test_crisis_faction_corpus.py` pins the
# exact `potential` shape of both technologies below, specifically so a future corpus revision
# that restructures either one (changes the flag name, removes the bypass branch, merges the two
# `has_technology` conditions, etc.) fails that test and forces this override back under review
# rather than silently keeping a stale classification.

# prerequisite-AND gate instead of a has_country_flag branch.
#
# Why this is 12 individual overrides and not a change to
# pipeline.crisis_faction.classify_by_prerequisite_inheritance's step-2 rule: step 2 requires
# EVERY rendered prerequisite of a technology to already share one faction before it inherits,
# deliberately -- these 12 each have a MIXED prerequisite set (one Standard-lane baseline weapon

# these 12 would apply generally, unaudited, across the rest of the 980-node corpus; a reviewed,
# individual override for each of the 12 -- verified against its own `prerequisites` list, exactly
# like every other entry in this file -- is the proportionate response instead.
