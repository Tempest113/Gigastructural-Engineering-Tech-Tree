# Field-consumption annotations (Item 3, client test-infrastructure task).
#
# tools/check_field_consumption.py walks schema/generated/dataset-types.ts for the full field
# list, then greps client/src/ for `.fieldName` references. A field that mechanical grep can't
# find gets ONE of two outcomes: real client/src/ consumption (nothing to do here), or a reviewed
# entry below. An entry for a field that no longer exists in dataset-types.ts is a hard error
# (stale-entry rot -- same discipline config/icon_overrides.txt already enforces).
#
# Format: one entry per line, `Interface.dotted.path | usage # justification`.
#   displayed   -- reaches the user, but not through a literal `.fieldName` grep hit (pre-rendered
#                  label text, groupId-derived equivalence, or another field's value stands in).
#   key-only    -- consumed only as a map/cache/lookup key, never itself DISPLAYED to the user.
#                  Distinguished from `displayed` because a naive grep for `.fieldName` treats
#                  both alike, which is exactly the imprecision this file exists to correct.
#   not-needed  -- a genuine KNOWN GAP: not consumed today, no shipped feature needs it. Every
#                  such entry MUST name the gap (issue/spec pointer) so the debt stays visible
#                  instead of silently laundered into "reviewed and fine."
#
# The six fields the original survey found unread (docs/BUILD-LOG.md): .weight, .variants,
# .source, .repositoryLink, .repeatableCostProgression, .overwriteDiff -- all below as KNOWN GAPS.
# This file's own build turned up MORE unconsumed fields than that survey named (schemaVersion
# validation on four of five artefacts, BaseDataset.metadata's "data as of" marker, .categories,
# .adjacency, .labelPriority, most of Diagnostics) -- also recorded honestly below, not narrowed
# back down to just the six the task description already knew about.

# --- Gate: known false positives (module docstring's own list) ------------------------------
# A gate's kind/refId/negated/alternative never appear by name in client code -- their
# information reaches the user through the gate's pre-rendered `label` string (built server-side
# by pipeline.dataset_emit's _gate_label_prefix -- "Needs X" / "Unavailable to X" / "or: X") and,
# for `alternative`, through `groupId`-derived equivalence (two gates sharing a groupId render as
# one OR choice; main.ts groups on groupId, never reads `alternative` directly). This is correct
# design, not a gap.
Gate.kind | displayed # Coded into Gate.label's own wording server-side; groupId-adjacent grep hits on the unrelated `edge.kind`/local `edgeCountByKindForStatus.alternative` are false-positive "consumed" matches this entry deliberately overrides.
Gate.refId | displayed # Coded into Gate.label's own wording server-side (the perk/technology/origin/civic name is interpolated into "Needs X"/"Unavailable to X" at build time).
Gate.negated | displayed # Coded into Gate.label's own wording ("Needs X" vs "Unavailable to X") -- see pipeline/gate_patterns.py's module docstring, "Negative gates" section.
Gate.alternative | displayed # Coded into Gate.label's own wording ("or: X") AND surfaced structurally via groupId (two gates sharing a groupId render as one OR choice in the popup).

# --- Identity/lookup keys (never themselves displayed) --------------------------------------

DetailPayload.technologyId | key-only # Used only to key the detailPayloadCache Map (src/dataset.ts) and to correlate a fetched payload with the popup currently open for that id -- never rendered as text.
SearchIndex.entries.technologyId | key-only # Used only to resolve a search-index entry back to its technology record/index (techIndexById) -- the rendered search-result text is the technology's displayed name, not this id.
