# Crisis-faction FLAG override config (D-7/P-5) — hand-maintained, checked in, loaded by
# pipeline/crisis_faction_flags.py, consumed by pipeline/crisis_faction.py's classify_by_flag.
#
# Distinct from config/crisis_faction_overrides.txt (which maps a TECHNOLOGY KEY directly to a
# faction, step 3 of D-7). This file maps a `has_country_flag` NAME, found in a technology's own
# `potential` block, to a faction — a technology whose `potential` references a mapped flag is
# classified to that faction, and (unlike the technology-key override) this classification feeds
# the SAME step-2 prerequisite-chain inheritance every other step-1 classification feeds, so
# technologies gated behind the flagged technology can inherit through the ordinary mechanism.
#
# Why this exists as a separate, narrow, hand-seeded map rather than a general
# `potential`-block flag-inspection rule: pipeline/crisis_faction.py's own module docstring
# records that general flag inspection was tried against the real corpus and rejected — of two
# candidates it surfaced, one was a confirmed false positive
# (giga_tech_tetradimensional_engineering) and the other needed individual reachability
# verification, not a name-pattern match (tech_sm_autocannons/tech_qnm_disruptors, now handled by
# the technology-key override instead). A blanket rule is still wrong. This file is the narrow
# alternative: each entry requires the same individual verification as an override, just applied
# to a flag identity instead of a technology identity, and is scoped to classify only the ONE
# technology whose `potential` sets that flag as its own gate — inheritance downstream is the
# ordinary step-2 mechanism, not this file reaching further than the one flag it names.
#
# Format: one entry per line, flag name/faction separated by ' = ', followed by a required '#'
# justification (never optional):
#
#   <has_country_flag name> = <faction: Aeternum | Blokkats | Compound | Sirenalia | Katzenartig Imperium>  # <justification>
#
# --- Real entries below ---
