## The failure being fixed

v1 computed the research path once, profile-blind, with `OR` branches flattened to inline
annotations instead of expanded. From a v1 screenshot of the path to `tech_mega_engineering`
(cost 74,750, regular/mechanical/non-nomadic):

- "or Arkship Mastery" (`tech_arkship_tier_3`) named an alternative to `tech_starbase_5` but never
  expanded its own prerequisite chain — incomplete for anyone actually taking that branch.
- "or Stingers" (`tech_stingers`) was shown as optional, alongside `tech_battleships`, when for a
  bio-shipset empire `tech_battleships` is **locked** (`potential` requires
  `country_uses_bio_ships = no`) and Stingers is the *only* route.
- `tech_starbase_5` was included for every empire, though it requires `is_nomadic = no` — a
  nomadic empire cannot research it at all and needs the Arkship branch instead.
- The running total (74,750) was consequently the regular/mechanical/non-nomadic figure,
  presented as if universal.

**Real corpus, confirmed against the actual data** (this is not a hypothetical worked example —
every number below came from actually running the algorithm this spec describes against the
vendored corpus): `tech_mega_engineering` has exactly the two `OR`-groups the screenshot's bug
implies —

```
tech_mega_engineering#alt0: tech_starbase_5  OR  tech_arkship_tier_3
tech_mega_engineering#alt1: tech_battleships OR  tech_stingers
```

| Profile | alt0 choice | alt1 choice | Total cost | Step count |
| --- | --- | --- | ---: | ---: |
| regular / mechanical / non-nomadic (v1's own case) | `tech_starbase_5` | `tech_battleships` | **74,750** | 15 |
| regular / mechanical / **nomadic** | `tech_arkship_tier_3` (starbase_5 is `locked`, `is_nomadic = no`) | `tech_battleships` | **99,750** | 21 |
| regular / **biological** / non-nomadic | `tech_starbase_5` | `tech_stingers` (battleships is `locked`, `country_uses_bio_ships = no`) | **73,750** | 15 |

74,750 for the exact profile v1 reported matches exactly — the fix changes what the OTHER eleven
profiles see, not that one. Note the nomadic total is **higher**, not lower, than the
non-nomadic one (99,750 vs 74,750) — correctness here means "the number this profile would
actually pay," not "a smaller, more flattering number." A fix that always produced a cheaper
total for the corrected profiles would itself be suspect.

## Trigger: selecting a technology, as in v1 — pinning a goal is explicitly deferred

**Confirmed in chat, this session, recorded so it is not built early or forgotten.** The research
path is shown for whichever technology the player currently has SELECTED (opened the popup for),
exactly as v1 did — there is no independent "goal technology" concept the path tracks
persistently while the player navigates elsewhere. Data-wise, this is already what
`researchPaths` being keyed by every rendered `technologyId` supports directly: the renderer looks
up whichever key the open popup names.

**Pinning a goal technology for always-on display (e.g., a persistent "path to X" overlay that
survives closing the popup and browsing other nodes) is a deferred quality-of-life feature,
explicitly OUT OF SCOPE for the first renderer.** It is not precluded by anything in this spec —
the same per-profile `researchPaths` data would serve it unchanged — but it is not being built now
and should not be inferred as implied scope from "the data already supports it." If it is wanted
later, it is a Stage 3 UI feature request to scope on its own terms, not a natural extension to
build alongside the selection-triggered path this spec actually specifies.

## Algorithm

Computed **per (technology, empire profile) pair**, at build time, over the empire overlay's
already-resolved edges and per-profile availability (P-14, P-13, D-14). One flat ordered list
with a running cost total, matching v1's presentation shape (confirmed wanted, kept
deliberately) — the fix is in what feeds that list and total, not the list's shape.

### 1. Only true `prerequisite` edges form the backbone

Same contract as today's `researchPaths` (P-12.9's existing row): the path is the complete
ancestor set reachable by walking `prerequisite` edges only, in topological order by tier. This
does not change. What changes is that `alternative` edges (P-14's `OR`-groups, previously ignored
by `researchPaths` entirely) are now resolved into the walk instead of being invisible.

### 2. `OR`-group resolution: viability filter, then cheapest total cost

At a technology with one or more `alternative` groups (`Edge.groupId`), each group's members are
filtered to **viable candidates** — those whose OWN per-profile availability state
(`pipeline.availability`, same evaluator P-13 already uses) is `available` or `uncertain` for the
selected profile. `locked` and `config-gated` candidates are excluded from selection entirely —
not because they can never be researched, but because presenting a route the player cannot
currently take, when a genuinely open alternative exists, is the exact "Stingers optional when
it's the only route" bug. Excluding `locked` is uncontroversial; excluding `config-gated` follows
the same "determinate-unavailable" reasoning decision 5 (below) applies to the target itself.

`uncertain` candidates ARE viable — excluding them would treat "we don't know" as "no," the
mistake D-10 already warns against for every other undecidable state in this project. An
`uncertain` branch can be chosen; if it is, the whole path inherits the uncertain-total treatment
(section 4).

**Among viable candidates, the chosen branch is the one with the cheapest TOTAL cost — the
branch's own cost plus its own full prerequisite chain's cumulative cost, recursively, not just
the branch member's own declared cost.** This is what fixes "Arkship Mastery never expanded its
own prerequisites": there is no such thing as a branch that isn't expanded, because expansion is
how its cost is computed in the first place. A step chosen via `OR`-resolution carries an
`alternatives` list of the OTHER viable (not chosen) candidates at that group, each with its own
per-profile-substituted name (D-14) — semantic data only, e.g. `[{"technologyId":
"tech_arkship_tier_3", "name": "Arkship Mastery"}]`, never a pre-composed sentence; Stage 3
renders "(via Starbase 5; Arkship Mastery route also available)" or equivalent from that plus the
chosen step's own name. Non-viable (locked/config-gated) siblings are never listed here — P-13's
own full twelve-profile matrix is where a curious player goes to see those, not the path view.

**Real corpus: fewest-steps and cheapest-total-cost never disagree.** Measured directly: of the
corpus's 35 real `OR`-groups (P-14) evaluated across all 12 profiles (420 group×profile
evaluations), 408 produce at least one viable candidate (see section 6 for the other 12); of
those 408, 72 involve a genuine choice among 2+ viable candidates, and **cheapest-total-cost and
fewest-steps agree on all 72 — zero disagreements.** Fewest-steps was considered as the tie-break
criterion and is recorded here as explicitly changeable, per instruction — but on the evidence
available, it would never have produced a different result, so this is not a case actively
observed to matter. If a future corpus revision produces a real disagreement, cheapest-total-cost
still governs per this decision, but that evidence should be revisited then, not before.

### 3. Per-profile name and icon (D-14)

Every step in the path — the chosen branch member, and every ordinary ancestor — renders under
the selected profile's D-14 substitution: `swapMappings`-resolved name/icon when an
axis-expressible swap is active for this profile, the base name/icon otherwise. A bio-shipset
player's path to `tech_fission_power`-adjacent chains says "Fission Metabolism," never "Fission
Power." This is presentation only — it does not change which technologies are ancestors, only how
each one's step is labelled.

### 4. `uncertain` steps stay in the path; the total becomes an ESTIMATE

An ancestor whose profile state is `uncertain` is not excluded — its own declared `cost` (a
static field, independent of availability state) is added to the running total exactly like an
`available` step, and it renders with an `uncertain` badge on that step rather than a different
list treatment. **The path's `totalCost` becomes an explicit estimate — a stated lower bound, not
a corrected/adjusted number** — the instant any step in it is `uncertain`: excluding the step
would understate the true cost (it might well be needed); presenting an exact total across an
unknown would be a confident claim resting on nothing. This must read as an ordinary annotated
state in the UI, not an error treatment, because **it will be common**.

**Counting rule (pinned; a later session corrected the original 163-182 range, which had no
defined meaning of its own): a path's uncertain-step count is always evaluated PER SELECTED
PROFILE, matching the path itself, which is per-profile by construction (section 1). "163-182"
was never a single figure — it was the per-profile minimum and maximum reported without saying
so.** The exact per-profile counts, out of 980 rendered technologies:

**Headline figure: 182/980 (18.6%)**, the worst (maximum) profile —
machine_intelligence/biological/non-nomadic — per the same worst-case convention D-10 already
uses for `profileDependentUncertainty`'s own ceiling/warn thresholds (CLAUDE.md's D-10 section:
"Hard ceiling: 10% for any single profile... worst-case"). Using the worst profile, not an
average or a range, keeps this figure comparable to that existing convention and avoids
understating what any one player could actually see.

**A separate, differently-defined figure also exists and is reported here labelled as such, so
neither is mistaken for the other**: 191/980 (19.5%) technologies have at least one uncertain
step in the path for AT LEAST ONE of the twelve profiles (the ACROSS-ANY-PROFILE / union figure —
relevant to "how many technologies could ever show this annotation to any player," not to what a
single selected profile sees). For completeness, the INTERSECTION — uncertain in EVERY profile's
path — is 156/980 (15.9%), the floor beneath which the per-profile figure never falls regardless
of which profile is selected. **The per-profile figure (182/980 worst-case) is canonical for any
UI-facing claim** ("N technologies show an estimated total for your empire"); the union and
intersection figures are corpus-characterisation figures only, not something a renderer states to
a player viewing one profile at a time.

All of this remains consistent with the ~21% unconditional-uncertainty figure D-10 already
established as a normal, expected feature of this corpus — none of these path-level figures is an
anomaly relative to it, they are the same underlying uncertainty surfacing through a different
lens (path membership vs. a technology's own state).

### 5. `config-gated`: only ever the path TARGET, never a mid-path step

**Confirmed (chat, this session): config-gated technologies are structural sinks, so decision 5
collapses to a single case.** Checked directly against the full typed-edge set (`prerequisite`
and `alternative` both): zero edges are sourced FROM any of the 50 `giga_tech_repeatable_*_cap`
technologies — extending D-13's existing Repeatables "sink property" finding (previously verified
for `prerequisite` edges only) to `alternative` edges too. **A `config-gated` technology can
therefore only ever be the QUERIED TARGET itself — it is structurally impossible for one to
appear as an interior ancestor of any other technology's path.** This is not a probabilistic
observation to hedge with a defensive fallback for the interior case; it follows from the same
graph structure D-13 already established, so this spec specifies the target-only case as the
ONLY case, not a common case with a general rule bolted on for a scenario that cannot occur.

A `config-gated` technology (D-10's fourth `AvailabilityState`) is **determinate-unavailable, not
uncertain**: the game knows the answer and it's "off," via a settings toggle, not "we don't
know." When the popup is opened for one of the 50 cap technologies directly, its path shows the
ordinary ancestor chain up to (not including) the technology itself — `totalCost` covers that
ancestor chain only. The target's own cost is excluded from `totalCost` entirely and its D-10
reason text (`Requires <Megastructure Name> cap: 1 + Repeatables`, subject sourced exactly as
`pipeline.dataset_emit._config_gated_subject`/`_swap_display_name` already do — never re-derived)
appears in the single `configGatedTarget` field (schema section below) — never folded into the
running total, never silently dropped, and never a second, general "config-gated steps" list,
since there is never more than the one entry.

**The distinction to hold onto**: `uncertain` means the tool does not know, so it says so and
still counts the cost (a stated lower bound). `config-gated` means the tool DOES know, and the
answer is "not under your current settings," so it counts the cost separately and says why. They
are not two flavours of the same annotation.

### 6. When there is no route at all — CORRECTED (Item 2d, a later session)

**The original text below claimed these two cases always coincide on the real corpus and could
share one presented state. That claim was wrong, and the error was found and reported honestly
rather than re-asserted: the real corpus has 78 technologies / 472 `(technology, profile)` pairs
where the target's own state is `available`/`uncertain` but a required ancestor is unreachable —
not the "exactly 2, always coinciding with the target's own lock" figure this section originally
recorded.** The two are genuinely different facts a player acts on differently, and the schema and
pipeline now say so:

- **`status: "unavailable"`** — the target's OWN availability state for this profile is `locked`.
  Nothing about the path matters; check the technology's own availability reason (shown in the
  P-13 panel above the path section).
- **`status: "blocked"`** (new) — the target's own state is `available`/`uncertain`, but a required
  ancestor is unreachable for this profile: either a non-`alternative` (true) prerequisite is
  itself `locked`/`config-gated`, or an `alternative` group has zero viable candidates.
  `researchPaths[key].blockedBy` names the specific blocking ancestor (`{technologyId, name,
  reason}`) — for a broken `alternative` group, one representative non-viable member, not every
  one. Nothing the player does about THIS technology helps until the named ancestor's own reason
  changes.

**Real corpus, current: 78 technologies / 472 `(technology, profile)` pairs are `blocked`.**
Categorised by cause (a survey done before the status split existed, re-confirmed unaffected by an
unrelated gate-polarity fix landed in between): 44 pairs trace to a broken ancestor's
`is_nomadic`-locked state (the `tech_starbase_*` chain and similar), 25 to an axis-locked ascension
perk ancestor (`ap_gigastructural_constructs` 10, `ap_galactic_wonders` 8, `ap_celestial_printing`
7), 4 to hive-mind/shipset-locked ancestors, 2 to a zero-viable `alternative` group, 3 unresolved
by that survey's quick trace (deeper nesting). Every traced case is a real, non-`alternative` dead
end — none is a modelling artefact (an ancestor "really" reachable another way the evaluator
missed). The originally-reported "2 technologies, both because the target itself is ALSO locked"
figure (`tech_growth_chamber_1`/`_2`, mechanical-shipset profiles) is real but was never
representative — it happened to be the only case surveyed at the time this section was written,
and the survey wasn't re-run against the full corpus before concluding the two cases "never
diverge." A documented claim is not self-verifying just because it cites a specific-sounding
number — see CLAUDE.md's `has_ancrel` writeup for the general form of this lesson.

**Presentation, never a blank list**: both `unavailable` and `blocked` carry no `steps` array —
`unavailable`'s reason lives in the P-13 panel above; `blocked`'s reason is `blockedBy` itself,
rendered as its own short explanatory line naming the blocking ancestor. `config-gated` targets
keep their own `status` value (section 5), not folded into either.

**The tripwire diagnostic stays, repurposed.** `diagnostics.unresolvableResearchPaths`
(`{technologyId, profile}[]`) now tracks every `blocked` pair directly — no longer "a case that
doesn't occur today," but the same real, always-current list the 78/472 figure above is drawn
from. A future re-vendor changing this count is expected corpus drift, not itself a bug signal;
what the diagnostic guards against is this list silently going out of sync with what `status:
"blocked"` actually reports.

**Moved again, same session, once Item 2b ("zero weight is an availability fact") landed
alongside this item: 78/472 → 958 (technology, profile) pairs / 116 distinct technologies.** Item
2b's weight-gate LOCKED downgrades add real new ancestor dead ends throughout the prerequisite
graph, and every downstream descendant of a newly-LOCKED technology legitimately becomes
`"blocked"` too — this is correct fallout of a real, separate fix landing in the same session, not
a defect in this item's own mechanism (already independently confirmed against raw source above).
Report the current, reconciled number; do not chase the smaller pre-Item-2b figure back down by
reverting either fix.

## Unresolvable (`null`) cost

15 of 980 rendered technologies have an unresolvable `cost` (5 apparently-free starting
technologies with no `cost` field at all; 10 vanilla "cosmic storm" technologies whose `cost` is
a dynamic modifier block, not a scalar — CLAUDE.md's "cost field present for every technology"
finding). **This is not a moot edge case for research paths**: measured directly, 8 of the 15
null-cost technologies ARE referenced as a `prerequisite` or `alternative` member of at least one
other technology, and **25 to 29 of 980 targets (2.5%–3.0%, varying by profile) have at least one
null-cost ancestor somewhere in their path.**

**Decision: a `null`-cost step contributes 0 to the running numeric total (never guessed at, never
treated as if the technology were free in the sense of "confirmed zero cost") but the path's
`totalCostIsEstimate` flag is set, with `"unresolved-cost"` recorded among the reasons** —
composing with the `uncertain`-availability reason (section 4) rather than replacing it; a path
can be an estimate for either or both reasons, and the emitted data says which. Treating `null` as
0 without flagging it would silently understate a real total (exactly the same failure mode
excluding `uncertain` steps would cause); treating it as some invented positive number would
fabricate data this pipeline has always refused to fabricate (D-4's "no evaluated weight"
precedent, same discipline applied to cost here). Flagging it and reporting the true minimum is
the only option consistent with this project's existing null-cost handling
(`base-dataset.schema.json`'s own `cost` field: "Never guessed at or defaulted to 0; a null cost
is an honest 'this tool can't state one'").

## Emitted data (so a renderer never recomputes traversal in the browser)

Lives in the empire-overlay artefact (already per-profile; P-13's `availability` and D-14's
`swapMappings` are the existing precedent for "per-profile display data computed once at build
time"), replacing `researchPaths`' current `{ancestors, shortestChain}` shape (itself a known v1
scope limitation per `pipeline/dataset_emit.py`'s own docstring — prerequisite-edges-only,
profile-blind since `OR`-groups were never resolved, and never accounted for a resolved
`@variable`/`inline_script` cost the way P-15's diff layer does).

Per technology, per profile:

```
researchPaths[technologyId] = {
  status: "path" | "config-gated" | "unavailable",

  // status == "path" or "config-gated" only:
  steps: [
    {
      technologyId,
      name,             // D-14-substituted for this profile
      icon,              // D-14-substituted IconRef for this profile
      tier,
      stepCost: number | null,
      availabilityState: "available" | "uncertain",   // never locked/config-gated -- excluded upstream
      groupId: string | null,       // set when this step was chosen from an OR-group
      alternatives: [{ technologyId, name }],  // other VIABLE (not locked/config-gated) siblings not chosen; [] when not applicable
    },
    ...
  ],
  totalCost: number | null,          // sum of stepCost, null-cost steps contributing 0
  totalCostIsEstimate: boolean,
  estimateReasons: ("uncertain-availability" | "unresolved-cost")[],   // [] when totalCostIsEstimate is false

  // status == "config-gated" only -- the target itself, excluded from steps/totalCost above:
  configGatedTarget: {
    technologyId, name, icon,        // D-14-substituted, matching the target's own card
    subject: string | null,          // D-10's configGatedSubject -- null when the megastructure name itself doesn't resolve (see D-10)
  } | null,

  // status == "unavailable" only -- no steps, no totalCost; renderer shows a short explanatory
  // line and defers to the availability panel already displayed for this technology/profile.
}
```

Nothing here requires the browser to walk `prerequisite`/`alternative` edges, evaluate
`OR`-group viability, or resolve D-14 substitution at render time — every field is already
resolved per profile at build time, matching P-12.9's existing "storing one canonical path and
substituting swaps in the browser is prohibited" implied decision (now generalised: nothing about
path SHAPE is computed client-side either, not just swap labels).

Additionally, `schema/diagnostics.schema.json` needs one new field when this spec is implemented:
`unresolvableResearchPaths: {technologyId, profile}[]` — section 6's tripwire diagnostic, same
shape convention as `swapsRenderingOnInheritedIcon` (D-14) and `tierPromotions`. Not part of the
empire-overlay artefact (diagnostics are their own lazy `?dev`-only artefact, S-2).

The "shortest chain" toggle named in P-12-detail-popup.md's original P-12.9 row is **retired by
this spec**, not carried forward: with `OR`-groups now resolved into the single path (per
decision 2), there is no longer a second, different "cheapest single chain" to toggle to — the
one computed path already is the cheapest-total-cost route. If a future need for a genuinely
different secondary view arises, it should be scoped fresh against whatever real gap motivates
it, not resurrected from v1's shape by default.

## Corpus figures, in full (six requested items)

1. **161 of 980 rendered technologies (16.4%) have a path whose ancestor STEP SET differs across
   at least two of the twelve profiles.** Largest observed step-count difference for one target
   across profiles: **30 steps** (`giga_tech_interstellar_ringworld`). Largest observed total-cost
   difference for one target across profiles: **131,000** (same target,
   `giga_tech_interstellar_ringworld`) — a single megastructure technology whose ancestor
   requirements vary dramatically by empire type.
2. **Cheapest-total-cost and fewest-steps never disagree in the real corpus** — 0 disagreements
   across all 72 genuine (2+ viable candidate) `OR`-group choices, and 0 across the full 408
   viable-candidate group×profile evaluations. Per the instruction's own framing: this means
   decision 2 (cheapest cost as the tie-break) is, on current evidence, not load-bearing against
   the simpler fewest-steps alternative — recorded as explicitly revisitable, not because it's
   wrong, but because the corpus offers no case that would currently distinguish them.
3. **182/980 (18.6%), the worst (maximum) profile, have a path containing at least one
   `uncertain` step — the canonical, per-profile figure (section 4's counting rule).** Range
   across all 12 profiles: 163 (best) to 182 (worst); across-any-profile union 191/980 (19.5%);
   intersection (uncertain in every profile) 156/980 (15.9%) — see section 4 for the full
   per-profile table and why the per-profile worst-case, not the range, is the headline number.
   **Exactly 50 of 980, in every profile, are themselves `config-gated`** (the cap-repeatable
   family; profile-invariant per D-10) — and, per the sink-property finding above, **zero paths
   contain a `config-gated` step other than as the target itself.**
4. **STALE, corrected by Item 2d (see section 6): the "exactly 2 of 980 impossible, never an
   ancestor-only case" claim was wrong.** Real corpus: `status: "unavailable"` (target itself
   locked) and `status: "blocked"` (ancestor chain broken, target itself fine) are genuinely
   different, both real — 78 technologies / 472 (technology, profile) pairs are `blocked`. Both
   are presented via an explicit `status`, never a blank or partially-populated list — see the
   rewritten section 6 for the current, correct contract.
